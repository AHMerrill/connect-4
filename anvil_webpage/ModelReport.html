Model Report

Training Neural Networks to Play Connect 4

🎯 The Challenge

Connect 4 is a solved game, but solving and playing are different engineering problems. Perfect play is known in theory, yet running full search on every move is too slow for a smooth web experience.

This project asks a practical question: can we train neural networks to imitate strong search decisions and deliver near-instant moves in production? To answer it, we trained two families of models on the same MCTS targets: a residual CNN and a lightweight Transformer.

Key Approach
Use MCTS as the teacher and neural networks as fast students: the policy head ranks columns, and the value head scores board quality on [-1, 1].

🧪 Scope of the Study

  • Supervision source: both models are trained on the same MCTS-generated policy/value targets, allowing architecture-level comparison under matched data quality.
  • Primary objective: maximize move quality while preserving near-instant inference suitable for a live web game.
  • Secondary objective: compare whether local-convolution inductive bias (CNN) or global-attention bias (Transformer) is more sample-efficient for Connect 4.
🧠 CNN Model
  • AlphaZero-style residual network
  • 10 residual blocks, 256 filters
  • ~75-78% top-1 (validation range)
  • Pattern-based recognition
⚡ Transformer Model
  • Vision Transformer (ViT) style
  • 6 layers, 8 attention heads
  • 77.29% top-1 (best logged run)
  • Attention-based relationships

📊 Training Data Generation

Rather than hard-code heuristics, we let Monte Carlo Tree Search (MCTS) teach the model what strong play looks like. For each board position, search provides a policy target (where to play) and a value target (how favorable the position is).

We used 2000 simulations per move, which gave a strong supervision signal without making data generation prohibitively expensive.

🎲 Diverse Game Coverage

A common failure mode in board-game datasets is over-representing opening states. To avoid that, we sampled 4 to 14 random opening moves with a right-tailed distribution before search-driven play.

That simple change increased exposure to tactical middle-game and end-game boards, where move quality matters most.

📦 Dataset Statistics
  • Raw positions: 703,111
  • After mirroring: 1,406,222
  • MCTS simulations: 2000/move
  • Board encoding: 6×7×2 tensor
🔄 Data Augmentation
  • Horizontal mirroring: Doubles dataset
  • Move-depth weighting: Balances game stages
  • Random openings: 4-14 moves (right-tailed)
  • Mirroring policy: Symmetric copies are intentionally kept

🎛️ Board Encoding

Each board position is encoded as a 6×7×2 tensor:

  • Channel 0: 1 where Player 1 (orange) has a chip, 0 elsewhere
  • Channel 1: 1 where Player 2 (white) has a chip, 0 elsewhere

This two-channel representation lets the network distinguish both players clearly. At inference time, the board is flipped in perspective when needed so the model always evaluates from the current player's view.

⚖️ Split and Weighting Strategy

  • CNN pipeline: move-depth balancing weights are applied and train/test split is stratified by depth bins to reduce early-game dominance.
  • Transformer pipeline: uses mirrored data with a random 90/10 train/validation split and callback-based model selection.
  • Interpretation note: absolute metrics depend on split protocol; cross-model comparisons are best treated as directional unless preprocessing is identical.

🧠 CNN Architecture

The CNN follows an AlphaZero-style residual design. It is built around a strong inductive bias for local geometry, which is useful for Connect 4 motifs like horizontal threats, vertical stacks, and tactical blocks.

⚡ Transformer Architecture

The Transformer uses a ViT-style formulation where each cell is a token. Self-attention lets the model connect distant board locations directly, which is useful for long-range dependency patterns that can be harder to capture with purely local filters.

🧭 Design Rationale

  • CNN rationale: preserves exact board geometry through same-padding convolutions and skip-connected residual refinement.
  • Transformer rationale: attention layers permit direct interaction between distant board cells without requiring many convolutional hops.
  • Two-head objective: policy supports move selection, value supports position scoring and future search integration.

⚖️ Model Comparison

  • CNN strengths: strong local tactical recognition and straightforward deployment as a single `.h5` model.
  • Transformer strengths: competitive policy accuracy with far fewer parameters than the CNN.
  • Trade-off: CNN has larger capacity; Transformer is more parameter-efficient.
  • Deployment note: live gameplay uses direct policy inference with legal-move masking (no in-game MCTS).

🔬 Model Selection Protocol

  • CNN search: compared 8 vs 10 residual blocks at two learning rates, then ran a targeted width increase from 128 to 256 filters.
  • Transformer selection: fixed architecture (6 layers, 8 heads, hidden 128) with EarlyStopping on validation policy accuracy.
  • Final CNN training: selected architecture retrained on the full mirrored dataset using a fixed epoch schedule for deployment export.

⚠️ Limitations and Validity Notes

  • Non-identical splits: CNN and Transformer used different split/weighting workflows, so metric comparisons are informative but not a strict controlled benchmark.
  • Metric scope: policy accuracy reflects imitation quality of MCTS labels, not guaranteed optimality in all board states.
  • Inference setting: deployed gameplay uses one-step policy inference, so tactical depth is lower than full-search MCTS at difficult positions.
  • Missing confidence intervals: most reported values come from best runs or ranges; repeated-seed statistics would strengthen scientific confidence.

☁️ Production Architecture

Deployment follows a clean separation of concerns: Anvil owns user interaction and board rendering, while a Dockerized AWS backend owns model loading and inference. This keeps frontend behavior responsive and backend logic testable.

Layer Responsibility
Anvil Frontend Game setup, board rendering, turn handling, user events, and API calls
AWS Backend Model loading, board preprocessing, move prediction, legality checks, fallback policy
Model Artifacts CNN loaded from `.h5`; Transformer rebuilt from code and loaded from `.weights.h5`

🔌 Inference API Contract

  • Input payload: `board` (6x7 ints), `current_player` (`plus/minus` or numeric), and `model_type` (`CNN/Transformer`).
  • Perspective normalization: if AI is second player, backend flips board sign so model always sees "current player" as positive channel.
  • Output payload: `recommended_move` plus metadata (`status`, `model_used`, `symmetry_applied`, `using_real_model`).

🛡️ Reliability and Fallbacks

  • Cold start behavior: models are loaded once at backend startup and cached in memory.
  • Legality enforcement: any invalid prediction is corrected to a legal column before returning to frontend.
  • Degraded mode: if model files are unavailable, backend uses a center-prior fallback move policy so gameplay remains functional.

🧾 Reproducibility Snapshot

  • Core artifacts: `cnn.h5` and `transformer.weights.h5` are the deployable model files expected by backend wrappers.
  • Main backend entry: inference requests are handled by `process_move(board_data)` through Anvil Uplink.
  • Deterministic safeguards: legal-move masking and center-prior fallback prevent broken gameplay even when predictions fail.
  • Environment expectation: Python + TensorFlow + NumPy stack in Dockerized AWS backend, with Anvil frontend calling HTTPS endpoint.

Aggregate accuracy hides where models actually break. These examples show a consistent pattern: immediate tactical motifs are easy, while multi-step planning positions remain difficult under one-pass inference.

💡 Key Insights

  • Immediate threats are easy: Both networks excel at recognizing "three in a row" patterns.
  • Early game is noisy: Opening moves have similar values, so confidence is lower.
  • Diagonal threats are trickier: Horizontal/vertical patterns are more common in training.
  • Strategic positions are hardest: Positions requiring long-term planning challenge the networks.
  • Center control emerges: The network learned that controlling center leads to more wins — an emergent strategy!

🤔 Why Some Boards Fail

  • Limited look-ahead: MCTS runs 2000 simulations; deployed networks make one forward-pass prediction.
  • Training data bias: Some rare tactical positions may not be well-represented in training.
  • "Equally good" problem: When multiple moves are similar, low confidence doesn't mean a bad move.
  • Rare tactical patterns: Unusual motifs (like double-threats) appear rarely and are harder to learn.

🛣️ Future Improvements

  • Unified evaluation protocol: train both architectures under the same split/weighting pipeline for cleaner apples-to-apples comparison.
  • Search-enhanced gameplay: add optional low-rollout MCTS at inference to improve tactical precision in hard mid-game states.
  • Calibration tracking: monitor policy/value calibration by move depth to target weaknesses instead of relying only on aggregate accuracy.
  • Self-play iteration: bootstrap stronger labels with model-guided search to improve difficult tactical patterns.
Conclusion
MCTS-quality supervision plus lightweight neural inference is a practical recipe for playable Connect 4 AI. The CNN offers higher capacity and familiar residual behavior; the Transformer reaches similar quality with far fewer parameters. For this deployment, both are strong enough to power an interactive product while preserving room for future search-enhanced upgrades.
